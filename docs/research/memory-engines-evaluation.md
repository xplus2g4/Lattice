# Evaluating Hindsight, Mnemosyne, Mem0, Cognee & Zep for a Course Knowledge Store

> Point-in-time evaluation, September 2026. Versions, licenses, stars, and pricing were checked then and are not maintained. Outcome recorded in [ADR 0001](../adr/0001-cognee-as-knowledge-engine.md).

## TL;DR
- **Cognee is the best direct fit** and the only one of the five that natively does what your project needs end-to-end: ingests slides/PDFs/PPTX, builds a queryable knowledge graph (Phase 2), supports dataset-scoped multi-tenancy (course-global + per-user), self-hosts under Apache-2.0, and can run on your existing Postgres/pgvector stack. **Zep/Graphiti** is a strong second for the graph layer but Zep's full memory product is now cloud-only. **Mem0** removed open-source graph memory in v3 (April 2026), gutting its Phase-2 value for self-hosters. **Hindsight** is excellent engineering but conversation/agent-memory-shaped, not document-corpus-shaped. **"Mnemosyne" is a research paper with no production implementation** worth adopting.
- Practically, you should **either adopt Cognee for ingestion + graph, or build a lean pgvector + concept-graph system yourself borrowing Cognee's ECL pipeline and Zep/Hindsight's shared-vs-user scoping.** All five are conversational-memory systems at heart; your use case is a curated document knowledge base, so expect to bend any of them.
- Phase 1 (retrieval) is solvable by any hybrid RAG. Phase 2 (surfacing "this relates to concept X from week 3") is the real differentiator and requires an explicit concept graph — which pushes you decisively toward Cognee (or a home-built graph) and away from Mem0 OSS.

## Key Findings
- **Hindsight** (Vectorize.io) — MIT license, arXiv:2512.12818 (Dec 2025), ~15.6K GitHub stars, actively developed. Real, polished implementation. Postgres+pgvector backend (embedded pg0 or external), local embeddings/reranker, four memory types (world/experience/observation/opinion), four-strategy TEMPR recall (semantic + BM25 + graph + temporal). Ingests PDF/PPTX/DOCX. Scoping is via "banks" + tags. Conversation-memory-shaped.
- **Mnemosyne** — arXiv:2510.08601 (Oct 2025), edge-device LLM memory; code exists only as paper supplementary material, no maintained production repo. Several unrelated GitHub projects share the name. **Not a usable foundation.**
- **Mem0** — Apache-2.0, over 41,000 GitHub stars (its own Oct 2025 announcement; ~56K+ on GitHub by mid-2026), YC S24, $24M raised. Strong drop-in memory API. **Open-source graph memory was removed in v3 (April 2026); graph is now Platform-only (paid).** OSS is now vector + entity-linking only.
- **Cognee** (Topoteretes UG, Berlin) — Apache-2.0, ~30K GitHub stars, $7.5M seed. Graph-native ECL (Extract-Cognify-Load) pipeline, hybrid vector+graph, dataset-level RBAC/multi-tenancy, ingests 38+ source types including PDF/PPTX. Best architectural match.
- **Zep / Graphiti** — Zep memory product is now cloud-only; Zep Community Edition was deprecated (April 2025, Apache-2.0 code frozen in `legacy/`). **Graphiti** (the temporal-KG engine, Apache-2.0, ~25K stars) remains self-hostable but requires you to build the app layer and provision a graph DB (Neo4j/FalkorDB).

## Details

### 1. Hindsight (Vectorize.io)
**What it is / maturity.** Open-source agent memory system, announced Dec 16, 2025 alongside the arXiv technical report "Hindsight is 20/20: Building Agent Memory that Retains, Recalls, and Reflects" (arXiv:2512.12818; authors Latimer, Boschi, Neeser, Bartholomew, Srivastava, Wang, Ramakrishnan; Vectorize.io + The Washington Post + Virginia Tech). MIT license. ~15.6K GitHub stars, very active release cadence (v0.4.x through 2026). Managed "Hindsight Cloud" also offered. A genuine, well-documented implementation, not a paper concept.

**Architecture.** Retain/Recall/Reflect operations. On retain, an LLM extracts facts, resolves entities, and builds temporal/semantic/entity/causal links, organizing memory into four networks: world facts, experience facts, observations (consolidated beliefs), and opinions. Recall runs four strategies in parallel (semantic vector, BM25 keyword, graph traversal, temporal), fused via Reciprocal Rank Fusion and cross-encoder reranking — this is "TEMPR." Reflect does agentic reasoning conditioned on a bank's behavioral profile ("CARA"). Storage: PostgreSQL (bundled embedded "pg0" or external Postgres 14+ with a vector extension). Embeddings default to local BAAI/bge-small-en-v1.5; reranker is a local cross-encoder. LLM (for extract/reflect) is pluggable (OpenAI, Anthropic, Gemini, Groq, Ollama, LM Studio, llama.cpp). Benchmarks (per arXiv:2512.12818): an OSS-20B backbone rises from 39.0% full-context to 83.6% on LongMemEval; with Gemini 3 Pro it reaches 91.4% (the paper claims the first agent-memory system past 90%) and 89.61% on LoCoMo versus 75.78% for the prior best open system.

**Multi-tenancy.** Unit of isolation is a "memory bank"; banks don't share data. Recommended pattern is one bank per user, or a shared bank with tags for cross-user scenarios. Endpoints are pathed `/v1/{tenant_id}/banks/{bank_id}/...` and every memory can be tagged (e.g. `user:alice`) with recall scoped by tag. **A single query cannot natively fuse two separate banks**; you would model course-global knowledge as one bank and layer user memory via tags in the same bank, or query two banks and merge in your app.

**Document ingestion.** Yes — the file-retain endpoint accepts PDF, DOCX, PPTX, XLSX, images (OCR), audio (transcription). Uses Markitdown for standard extraction or "Iris" AI extraction for complex layouts. Content is chunked, chunks stored alongside extracted facts, documents tracked by `document_id`.

**Relation retrieval (Phase 2).** Graph links (semantic/entity/temporal/causal) are built and graph traversal is one of the four recall strategies. Entities are extracted and linked; you can filter/list memories by linked entity. However, the graph is oriented around facts/entities extracted from ingested text, not an explicit "concept prerequisite" course graph, and there is no prebuilt "related concepts" API — you'd surface relations via entity links.

**Self-hosting.** Excellent. One Docker command, Helm charts, or pip. Fully local stack possible (embedded Postgres + local embeddings + local LLM via Ollama). A background worker is required for observation consolidation. Cost profile: compute + storage + per-token LLM cost for extraction/reflection only (recall is LLM-free).

**Limitations.** Conversation/agent-memory-shaped: it "learns" from streams and forms opinions/mental models — powerful but more machinery than a course knowledge base needs. No cross-bank query. Four-memory-type/three-op model adds developer surface area. Observation consolidation is ongoing background cost.

**Verdict: Use partially / borrow architecture.** Great for the per-user memory tier and as a reference for hybrid multi-strategy recall, but its bank model and agent-experience framing fight the shared-course-corpus requirement. Not the primary foundation.

### 2. Mnemosyne
**What it is.** The relevant LLM-memory reference is arXiv:2510.08601 (Oct 2025), "Mnemosyne: An Unsupervised, Human-Inspired Long-Term Memory Architecture for Edge-Based LLMs" (Aneesh Jonelagadda et al.). It uses graph-structured storage, substance/redundancy filters, memory committing/pruning, probabilistic recall with temporal decay, and a "core summary." Evaluated on longitudinal healthcare dialogues and LoCoMo (highest reported LoCoMo temporal-reasoning and single-hop scores among same-backbone methods; 65.8% blind human-eval win rate). Code is provided only as supplementary material to the paper; **there is no maintained, production-grade open-source repo of this system.** Multiple unrelated GitHub projects named "mnemosyne" exist (a Hermes-agent memory plugin, a Rust code-retrieval engine, a SQLite cognitive-memory toy) — none is the paper's system and none is a serious knowledge-store foundation.

**Verdict: Not a fit (paper-only).** Borrow one idea if anything — temporal decay / consolidation for the per-user memory tier — but there is nothing to adopt directly. Usefully, the Mnemosyne paper itself provides a well-argued critique of the LoCoMo benchmark (highly inaccurate gold answers, e.g. a "degree in political science" gold answer contradicted by the source conversation), valuable context when reading other systems' benchmark claims.

### 3. Mem0
**What it is / maturity.** "mem-zero," Apache-2.0, over 41,000 GitHub stars at its Oct 28, 2025 funding announcement (~56K+ on GitHub by mid-2026), 14M+ downloads, YC S24. **Raised $24M — a $3.9M seed led by Kindred Ventures plus a $20M Series A led by Basis Set Ventures (with Peak XV, GitHub Fund, and Y Combinator).** The most polished drop-in memory API in the category, with hosted Platform + self-hosted OSS. Self-host stack is three Docker containers: FastAPI server, PostgreSQL+pgvector, and (formerly) Neo4j.

**Architecture & the critical v3 change.** Mem0 stores extracted facts across a vector DB (20+ backends incl. pgvector, Qdrant) with multi-level scoping (user_id / agent_id / run_id; user/session/agent). **In the v3 OSS rewrite (SDK v2.0.0, released 2026-04-16, PR #4805) Mem0 removed all external graph-store drivers (Neo4j, Memgraph, Kuzu, Apache AGE, Neptune) — ~4000 lines deleted.** Graph memory is now a Platform-only (paid, hosted) feature with no OSS equivalent. OSS v3 replaced it with lightweight entity linking (spaCy-extracted entities in a parallel vector collection, used only to boost hybrid-search ranking). Extraction is now single-pass ADD-only. Retrieval fuses semantic + BM25 + entity matching.

**Multi-tenancy.** Strong: user_id/agent_id/run_id scoping is first-class. But no shared-graph + user-graph fusion in OSS; you'd model course knowledge as one namespace and merge in-app.

**Document ingestion.** Mem0 is built for conversational messages/facts, not document corpora. No native PDF/PPTX ingestion or layout-aware chunking — you'd pre-parse documents yourself.

**Relation retrieval (Phase 2).** In OSS, effectively gone — only entity-match ranking boosts, no traversable graph, no `relations` field returned. Phase 2 "related concepts" would require the paid Platform or a graph you bolt on yourself.

**Benchmarks/criticism.** Mem0's LoCoMo SOTA claims were publicly disputed by Zep, which argued the benchmark is flawed and that Mem0's Zep implementation was misconfigured. LoCoMo is widely criticized (short ~16–26K-token contexts, inaccurate gold answers; Letta showed a filesystem baseline hits 74%).

**Verdict: Not a fit for Phase 2 (self-hosted); partial for Phase 1.** The v3 removal of OSS graph memory is disqualifying for your relation-retrieval goal unless you pay for Platform. Its document-ingestion gap is a second strike. Borrow its clean user/agent/run scoping API design.

### 4. Cognee (Topoteretes)
**What it is / maturity.** Open-source "AI memory engine," Apache-2.0. GitHub currently shows ~30K stars (an earlier company blog cited 12K+, indicating rapid growth through 2026). **$7.5M seed (closed Feb 2026, led by Pebblebed — Pamela Vagata ex-OpenAI and Keith Adams ex-FAIR — with 42CAP and Vermilion Ventures);** founded 2024 by Vasilije Markovic and Boris Arzentar; used at 70+ companies including Bayer (processing 10,000 scientific papers) and the University of Wyoming. Real, actively developed implementation with Python API, CLI, REST API (FastAPI), and MCP server. Paper: arXiv:2505.24478 ("Optimizing the Interface Between Knowledge Graphs and LLMs for Complex Reasoning"). Reports state-of-the-art on the BEAM benchmark (0.79 at 100K tokens vs prior 0.735; 0.67 at 10M vs 0.641).

**Architecture — the best match.** ECL pipeline: `add` (ingest raw data) → `cognify` (LLM extracts entities/relationships, chunks, summarizes, embeds into both graph and vector stores) → optional `memify` (feedback refinement) → `search`. Unifies three storage layers (relational + vector + graph). **The default local stack is fully embedded and file-based: SQLite (relational) + LanceDB (vector) + Kuzu (graph)** — zero infrastructure ("pip install cognee and an OpenAI key gets you running"). **For production it runs on your existing Postgres/pgvector** (relational + vector) with Kuzu or Neo4j for the graph. `docker compose up` starts just the API on :8000; Postgres and Neo4j are optional profiles (`--profile postgres`, `--profile neo4j`). Note: using Postgres *itself* as the graph store is a demo-only feature — the README states "the production ready feature is available as a licenced product" — but the Kuzu/Neo4j graph backends are fully open.

**Multi-tenancy — fits the two-tier design.** Permissions revolve around "datasets" (self-contained bundles of documents + their graph/vector representations). Principals = users, roles, tenants; grants = Read/Write/Delete/Share. With `ENABLE_BACKEND_ACCESS_CONTROL=true` each user+dataset gets isolated graph/vector DBs. **Crucially, a single search can span multiple datasets you can read** — the docs state "searches run against one or more datasets you can read" and "this scope can contain multiple datasets" — with results tagged by `dataset_name`/`dataset_id`. This maps directly onto your requirement: a shared **course dataset** + a **per-user private dataset**, queried together in one call. (Caveats: `AGENTIC_COMPLETION` requires exactly one dataset; and there is documented confusion about the true default of the access-control flag — GitHub issue #2103.)

**Document ingestion.** Native. `add()` accepts text, file paths, URLs, binary streams; supported formats include PDF and Office docs (.docx, .pptx), across 38+ source types. cognify classifies documents, chunks, extracts entities/relationships via LLM, generates summaries, and embeds into vector + graph. (PDF-parsing quality has been an active improvement area — issue #1342.)

**Relation retrieval (Phase 2) — strongest here.** Multiple search types expose the graph: `GRAPH_COMPLETION` (natural-language answers via graph traversal — "understanding how concepts relate"), `INSIGHTS` (MCP-only; returns raw relationship triplets as readable "related concept" lines), plus `RAG_COMPLETION`, `CHUNKS`, `SUMMARIES`, and `FEELING_LUCKY` (auto-routes). Hybrid completion appends a "## Related facts" section of edge-derived facts ranked by query similarity. Supports OWL/RDF ontologies for domain schemas (e.g. a course concept hierarchy: Topic → Concept with prerequisite edges) and can infer via hierarchy/transitive relations. This is exactly the machinery to say "this relates to concept X you saw in week 3."

**Self-hosting.** Strong and flexible: pip for embedded, docker-compose for services; runs on your GCP + Docker + Postgres. LLM/embeddings pluggable (OpenAI default; local Ollama supported). Cost = compute + per-token LLM cost during cognify (ingestion is LLM-heavy; retrieval can be cheaper).

**Limitations.** cognify is LLM-cost- and latency-heavy on large corpora. Pipeline-first architecture has a learning curve. Extraction quality depends on your LLM and ontology. Postgres-as-graph is paywalled (use Kuzu/Neo4j instead). Multi-tenant isolation requires both graph and vector backends to support isolation (LanceDB/pgvector + Kuzu/Neo4j do).

**Verdict: Use directly (primary recommendation), or borrow its ECL + dataset model.** It is the only one of the five purpose-built for structured document-to-graph knowledge with multi-dataset querying and native slide/PDF ingestion. It hits Phase 1, Phase 2, and your two-tier scoping in one system.

### 5. Zep / Graphiti
**What it is / maturity.** Zep is a memory layer built on Graphiti, a temporal knowledge-graph engine (arXiv:2501.13956, "Zep: A Temporal Knowledge Graph Architecture for Agent Memory"). **Two licensing facts matter:** (1) Zep **Community Edition was deprecated in April 2025** — the repo is frozen under Apache-2.0 in a `legacy/` folder, no updates or support; the Zep product is now **cloud-only** (SaaS, credit-based, SOC2/HIPAA). (2) **Graphiti remains open-source (Apache-2.0, ~25K stars) and self-hostable** as a library, and is where Zep now concentrates its OSS effort.

**Architecture.** Graphiti builds temporally-aware knowledge graphs from episodes (messages, JSON, unstructured text): entities as nodes, facts as edges ("triplets"), with a bi-temporal model (valid_at / invalid_at / ingested times) enabling point-in-time queries and fact invalidation. Retrieval combines semantic + BM25 + graph traversal in one ranked call, with no LLM-in-the-loop (Zep reports P95 ~300ms). Backends: Neo4j 5.26, FalkorDB, Amazon Neptune (+ OpenSearch); Kuzu is now deprecated (upstream archived). Requires an LLM with structured output (OpenAI/Anthropic/Gemini) for ingestion; smaller local models often fail schema extraction.

**Multi-tenancy.** In Zep Cloud: user graphs (per user_id) + group/standalone graphs (group_id/graph_id) for shared org knowledge; a chatbot can retrieve from both a user's graph and a shared group graph and merge context — a clean template for your two tiers. In raw Graphiti you implement this yourself via graph partitioning / group_id namespacing.

**Document ingestion.** Graphiti ingests episodes of text/JSON; it is **not** a document/slide ingestion pipeline — no native PDF/PPTX parsing or layout chunking. You'd parse documents to text/JSON first (e.g. with Docling) then feed episodes.

**Relation retrieval (Phase 2).** Excellent graph substrate — entities, typed edges, temporal validity, graph traversal in retrieval. Best-in-class for evolving/temporal facts. But you build the "related concept" surfacing on top of Graphiti's node/edge APIs; there's no prebuilt course-concept "related nodes" endpoint.

**Self-hosting.** Graphiti library: yes (pip), but you must run and manage a graph DB (Neo4j/FalkorDB) and build the entire application/scoping layer. The turnkey Zep memory service is no longer self-hostable.

**Limitations.** Full product is cloud-only (a hard blocker for self-host-preferred teams). Graphiti alone is a graph engine, not a knowledge-store product — significant build effort. LLM-with-structured-output dependency. Document ingestion must be built. Zep publicly disputes Mem0's benchmarks; treat all vendor SOTA claims skeptically.

**Verdict: Borrow architecture (Graphiti) / use Graphiti as a component.** Adopt Graphiti if temporal fact-evolution matters or you want a battle-tested temporal-KG engine, and copy Zep's user-graph + group-graph scoping pattern. But it is not a drop-in course knowledge store, and Zep's cloud-only pivot removes it as a self-hosted turnkey option.

## Recommendations

**Stage 1 — Adopt Cognee as the foundation (recommended default).** It is the only named system that satisfies Phase 1, Phase 2, document ingestion, and your two-tier scoping simultaneously, and it runs on your GCP + Docker + Postgres. Concretely:
- **Model course-global knowledge as one Cognee `dataset` per course** (e.g. `cs101-global`), ingesting slides (PDF/PPTX), tutorials, and instructor memos via `add()` → `cognify()`. Grant all students **Read** on it.
- **Model each user's private notes as a per-user dataset** (`cs101-user-<id>`) with Write for that user only.
- **Serve queries with `ENABLE_BACKEND_ACCESS_CONTROL=true` and pass both datasets** (`[cs101-global, cs101-user-<id>]`) to a single `search()`; results return tagged by dataset so you can show provenance ("from course slides" vs "from your notes").
- **Phase 1** = `RAG_COMPLETION` or `GRAPH_COMPLETION`. **Phase 2** = `INSIGHTS` (raw related-concept triplets) or the "## Related facts" section of hybrid completion; define an **OWL/RDF ontology** for course concepts (Topic→Concept, `prerequisite_of`, `related_to`, `introduced_in_week`) so the system can say "this relates to concept X from week 3."
- Use **Kuzu (embedded) or Neo4j** for the graph — avoid the paywalled Postgres-as-graph feature. Use **pgvector on your existing Postgres** for vectors.
- **Benchmark to proceed:** ingest one real course and verify (a) cross-dataset queries return fused, correctly-scoped results and (b) INSIGHTS surfaces sensible related concepts. If cognify cost/latency on a full course is acceptable and relation quality is good, commit to Cognee.

**Stage 2 — If Cognee's cognify cost/latency or extraction quality disappoints, build your own two-tier store, borrowing patterns:** pgvector for hybrid retrieval (you already run Postgres) + a lightweight concept graph (a Postgres edge table, or Kuzu/Neo4j). Borrow: **Cognee's ECL** (parse → LLM entity/concept extraction against a course ontology → load to graph+vector); **Zep's user-graph + group-graph split** for global-vs-user scoping (and its temporal edge model if you need "facts change over time"); **Hindsight's four-strategy RRF recall** (semantic + BM25 + graph + temporal, cross-encoder rerank) for retrieval quality. Parse slides with Docling (native PDF/PPTX). Phase 2 = a `concepts` table + `concept_edges(prerequisite_of, related_to, week)`; on answering, look up concepts touched by retrieved chunks and traverse one hop to surface "related concept" hints.

**Stage 3 — Layered option:** use **Graphiti** as the concept-graph engine (if temporal fact-evolution matters) behind your own app + pgvector, and/or use **Hindsight** solely for the per-user memory tier (a bank per student) while your global course store is pgvector/Cognee. This has more moving parts; only do it if a single system underperforms on one tier.

**Do not:** rely on Mem0 OSS for Phase 2 (graph removed April 2026), adopt Zep's cloud product if self-hosting is required, or attempt to use "Mnemosyne" as a codebase.

**Thresholds that change the recommendation:** If you need **temporal/versioned knowledge** (materials change across semesters; "what did the syllabus say in week 3") → weight Graphiti/the Zep pattern higher. If **ingestion cost** must be near-zero → skip LLM-extraction systems and do plain pgvector RAG + a hand-built concept graph. If you later need **managed SOC2/HIPAA** → Zep Cloud or Mem0/Cognee cloud become viable.

## Caveats
- **Fast-moving space (data current September 2026).** License and feature facts are version-sensitive: Mem0's OSS graph removal (v3, April 2026), Zep CE deprecation (April 2025) and cloud-only pivot, and Kuzu's deprecation across Graphiti and Cognee after Kuzu was archived/acquired upstream. Re-verify before committing.
- **Star counts and funding are approximate** and drawn from mixed primary/secondary sources (e.g. Cognee is cited at 12K stars in an older company blog but ~30K on GitHub now; Mem0 at 41K at its Oct 2025 raise and ~56K+ by mid-2026). Treat these as directional maturity signals, not precise figures.
- **Benchmark claims (LoCoMo, LongMemEval, BEAM) are contested.** LoCoMo has documented flaws (short contexts, inaccurate gold answers; a filesystem baseline scored 74%), and vendors dispute each other's numbers (Zep vs Mem0). Do not select on leaderboard scores; run your own course-corpus eval.
- **All five are fundamentally conversational/agent-memory systems.** Your use case is a curated document knowledge base that students query — a RAG/knowledge-store problem. Cognee bends most naturally to it; the others require adaptation. A plain pgvector RAG + concept graph remains a legitimate, lower-magic alternative.
- **Cognee's `ENABLE_BACKEND_ACCESS_CONTROL` default is documented ambiguously** (GitHub issue #2103); test the flag's behavior explicitly rather than trusting the default. Multi-tenant isolation requires both graph and vector backends to support it.
- **Adjacent tools worth knowing** (not evaluated in depth): LightRAG and Microsoft GraphRAG (graph-RAG over documents, closer to your problem than most of the five); LlamaIndex KnowledgeGraphIndex (quick concept-graph build); Letta/MemGPT (agent memory management — a Letta filesystem baseline scored 74% on LoCoMo, but it is not a document store); and plain pgvector RAG (your baseline). LightRAG or GraphRAG could substitute for Cognee if you want lighter graph-RAG without the full memory-engine framing.
